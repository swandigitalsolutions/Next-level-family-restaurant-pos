# Deploying the AWS build

Firebase (`firebase/`) is the live system and stays untouched throughout.
This deploys a **separate, independent** AWS stack. Nothing here is
reversible-free — read this whole file before running anything, and do it
against a throwaway/new AWS account first, not one with other workloads.

## 0. What you need before starting

- AWS **programmatic credentials** (access key + secret, or an SSO profile) —
  NOT your console password. `aws configure` or `aws sso login` sets these up.
  Least-privilege is better, but for a first deploy `AdministratorAccess` on a
  dedicated IAM user in a throwaway account is the pragmatic choice.
- Node 20+, the AWS CLI v2, and `npx` available in the shell you deploy from.
- A decision on Razorpay: go live with `ALLOW_MOCK_PAYMENTS=true` (website
  checkout uses a fake provider, everything else is real) or have real
  Razorpay test/live keys ready. Either is fine to start; mock can be
  switched to real later with zero code changes (see step 4).

## 1. One-time account setup

```bash
cd aws/infra
npm install
npx cdk bootstrap aws://<ACCOUNT_ID>/ap-south-1
```

`cdk bootstrap` creates the S3 bucket + IAM roles CDK itself needs. Run once
per account+region.

## 2. Validate before touching AWS for real

```bash
cd aws/backend && npm install && npm run build && npx tsc --noEmit && npx eslint src --ext .ts
cd ../infra && npm install
npx cdk synth --context env=dev   # should produce 6 templates, no errors (a
                                   # synth-time "no credentials" annotation
                                   # disappears once real creds are configured)
```

If this step fails, stop — do not proceed to a real deploy.

## 3. Create the secrets CDK expects to already exist

CDK references these by name but does not create their *values* (a value
only a human should set, never generated by code). Run
`aws/db/scripts/create-secrets.sh <env>` (see that file for what it does), or
by hand:

```bash
aws secretsmanager create-secret --name nlpos-dev/website-api-key \
  --secret-string "$(openssl rand -hex 32)"

aws secretsmanager create-secret --name nlpos-dev/razorpay \
  --secret-string '{"keyId":"rzp_test_xxx","keySecret":"xxx","webhookSecret":"xxx"}'
```

Going live with mock payments instead: still create the `razorpay` secret
(the JSON keys can be placeholders — `paymentProvider` stays `mock` by
default so it's never read) so a later switch to real Razorpay is a context
flag, not a redeploy of secrets.

The **database** secret is created automatically by the `DatabaseStack`
(Aurora's own managed secret) — nothing to do there.

## 4. Deploy, stack by stack, verifying each one

```bash
cd aws/infra
npx cdk deploy nlpos-dev-network --context env=dev
npx cdk deploy nlpos-dev-database --context env=dev   # ~10 min (Aurora)
npx cdk deploy nlpos-dev-auth --context env=dev
npx cdk deploy nlpos-dev-realtime --context env=dev
npx cdk deploy nlpos-dev-api --context env=dev \
  --context paymentProvider=mock --context allowMockPayments=true
  # once real Razorpay keys are in the secret: --context paymentProvider=razorpay
npx cdk deploy nlpos-dev-hosting --context env=dev
```

After `network`+`database`, note the RDS Proxy endpoint and secret ARN from
the stack outputs (also fetchable via `aws cloudformation describe-stacks`).

## 5. Initialize the database

```bash
psql "$(aws secretsmanager get-secret-value --secret-id <db-secret-arn> --query SecretString --output text | jq -r '"postgresql://\(.username):\(.password)@<proxy-endpoint>:5432/posdb"')" \
  -f aws/db/migrations/001_init.sql
# then, as the cluster's master user, create pos_app and run:
psql ... -f aws/db/migrations/002_privileges.sql
```

## 6. Point the frontend at the real endpoints

Fill in `aws/hosting/js/aws-config.js` with the `ApiEndpoint` (ApiStack
output) and `WebSocketEndpoint` (RealtimeStack output), then redeploy just
the hosting stack: `npx cdk deploy nlpos-dev-hosting --context env=dev`.

## 7. First real smoke test — do this before any data migration

1. Create one admin account directly via AWS CLI (`aws cognito-idp
   admin-create-user` + `admin-set-user-password`) and a matching row in
   `users`/`user_credentials` — or run the ETL with a tiny test dataset first.
2. Load the deployed site URL (CloudFront domain from the hosting stack
   output), sign in, confirm the dashboard loads.
3. Open the Kitchen screen in one tab, accept a QR test order in another,
   confirm the WebSocket push + chime actually fires. **This is the single
   most likely thing to need real debugging** — it has never run against
   real AWS before this deploy.
4. Exercise one write path per role (billing, manager, kitchen, cafe_billing)
   to confirm the Cognito role claim is actually being enforced end to end.

Do not consider this "working" until step 7 has actually been done and
observed — not assumed from the code.

## 8. Data migration (only after step 7 passes)

```bash
cd aws/db && npm install
GOOGLE_APPLICATION_CREDENTIALS=<service-account.json> \
  node scripts/migrate-from-firestore.mjs --dry --project <firebase-project-id>
# review the counts, then:
node scripts/migrate-from-firestore.mjs --project <firebase-project-id> --target staging
node scripts/migrate-from-firestore.mjs --verify --project <firebase-project-id> --target staging
```

Never run with `--target production` until staging has been fully verified
by a human, per the explicit opt-in flag required on that path.

## Rollback

Nothing here touches Firebase. If the AWS deploy has problems, the
rollback is simply: keep serving staff/customers from the existing Firebase
deployment and `cdk destroy` (or just abandon) the AWS stacks. There is no
shared state between the two systems to un-wind.
